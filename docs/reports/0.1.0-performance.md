# 0.1.0 performance

Measured performance, memory, incremental and query baseline of grammar
version 0.1.0 (Session 05, 2026-09-23/24 UTC). It is a release baseline,
not a speed claim: it states what was measured on one machine and that no
material performance problem was found. Every number is an empirical
observation for the inputs and machine below, not a guarantee. Raw samples,
inputs and scripts are local evidence
(`artifacts/session-05-final-release-freeze/04-performance/`, identity
`EVIDENCE-SHA256SUMS` = `0fa05e41965332762963d83d359ea1b36ee5e497b91bdd63b75a281a822b290d`).

## Identity and environment

| Item | Value |
|---|---|
| Grammar | `src/parser.c` `fec46d21914ccedb1242f068059262bd51130bb3e7b6aefb7acab9bb0d6c1d86`, measured at `e863474` (Session 05 changed no grammar file, so the numbers also hold for the Session 04 `main` `2aeb29d`) |
| Native runtime | Tree-sitter `lib/` at tag `v0.27.0` (`6070dbfe`), compiled from source with gcc 16.2.0 (MSYS2 ucrt64) `-O2`, linked with the generated `parser.c` into a local harness (`bench.c`, not shipped) |
| CLI | tree-sitter 0.27.0, windows-x64 binary `9fbc4f28…`, run through `scripts/tscli.py` (verified) |
| Machine | Intel Core Ultra 9 285H, 16 logical CPUs, 31.5 GiB RAM, Windows 11 (10.0.26200), no other benchmark running |
| Harness check | For all 230 W12 inputs the harness gives the CLI's tree and error state (the only differences are the `MISSING`/`UNEXPECTED` annotations that `ts_node_string` prints and the CLI's default output omits) |

Method: warm-up parses first (3, 2 or 1 by size), then 30 timed parses
below 200 KB, 10 up to 2 MB and 5 above; one parser object, a fresh parse
each time, `QueryPerformanceCounter` around `ts_parser_parse_string` only.
p50 is the median; p95 is given where n ≥ 20. Peak memory is the peak
working set of a separate process that parses the input once (it includes
the input buffer, the process and the runtime; it is not parser-owned
accounting). Every input's error state was checked: all valid inputs parse
with no error, all malformed inputs with one.

About 26–30 ms of every run is process start and loading the compiled
parser. Wall-time p95 reached 130–215 ms on this host for small inputs
(background load); single CLI wall times are therefore not a performance
measure.

## Incremental parsing (native)

Base: the 100 KB input above. Each edit is applied with `ts_tree_edit` and
reparsed with the old tree; the result is compared with a fresh parse of
the edited text (`ts_node_string`, identical in every case). n = 30.

| Edit | Incremental p50 (p95) | Fresh p50 | Ratio |
|---|---|---|---|
| one-byte identifier edit | 446.6 µs (1.06 ms) | 26.11 ms | 0.017 |
| literal replacement | 338.4 µs (671.6 µs) | 25.33 ms | 0.013 |
| operator replacement | 415.2 µs (722.9 µs) | 24.38 ms | 0.017 |
| line insertion | 431.5 µs (842.0 µs) | 24.10 ms | 0.018 |
| line deletion | 391.0 µs (679.2 µs) | 23.71 ms | 0.016 |
| block insertion (IF) | 414.4 µs (824.7 µs) | 24.31 ms | 0.017 |
| block deletion (WHILE) | 369.4 µs (624.5 µs) | 23.78 ms | 0.016 |
| edit inside nested FOR/FOR | 494.2 µs (1.13 ms) | 27.37 ms | 0.018 |
| syntax error (`(` inserted), then repaired | 520.0 µs (954.6 µs); repair 616.0 µs | 29.42 ms | 0.018 |

The repaired tree equals the original tree. The ratios are recorded, not
used as thresholds. Incremental correctness of the W10 scripts is gated
separately (V5).

## Highlight query (native)

`queries/highlights.scm`: compiles in 0.8–1.6 ms; running all captures takes
215.2 µs for `program.brs` (766 captures), 8.32 ms for 100 KB (24,550),
112.29 ms for 1 MB (239,608) and 505.19 ms for 5 MB (1,196,076), linear in
the number of captures. No pathological query behaviour was seen.

## Comparison with the legacy grammar (informational)

Same harness and runtime, same machine, on inputs that all three grammars
parse without an error (a function using assignments, IF/ELSE, FOR, WHILE,

| Input | 0.1.0 p50 | legacy `253fdfaa` | legacy `0c534d56` | Peak WS (0.1.0 / 253fdfaa / 0c534d56) |
|---|---|---|---|---|
| 207 B | 42.5 µs | 64.7 µs | 71.0 µs | 4.4 / 4.5 / 4.5 MiB |

| 880,890 B | 291.95 ms | 451.13 ms | 492.07 ms | 43.9 / 62.4 / 68.2 MiB |

On this subset 0.1.0 builds smaller trees (315,001 nodes against 487,201 and
550,201 at 880 KB) and is about 1.5–1.9 times faster. The legacy grammar
rejects much documented syntax
([0.1.0-comparative-conformance.md](0.1.0-comparative-conformance.md)), so
the comparison covers only this subset.

## Validation-tool cost (S04-H5)

`parse --cst` output grows with tree depth squared (indentation and a parent
lookup per node, CLI source `crates/cli/src/parse.rs` @ `v0.27.0`), so the
old error-state check timed out on deep valid input although the parse was
fast. Session 05 reads only the root line (`scripts/tscli.py` `has_error`):

| Input | Parse (CLI `--time`) | Old check (full `--cst`) | New check |
|---|---|---|---|
| binary chain, 100,000 operands (valid) | 165.5 ms | > 60 s (timeout) | 0.23 s |
| nested IF, depth 2,000 (valid) | 8.8 ms | 1.29 s | 0.035 s |
| nested parentheses, 5,000 (valid) | 8.4 ms | 1.14 s | 0.20 s |
| 100,000 bare-CR lines (invalid) | 2,874.1 ms | > 60 s (timeout) | 2.63 s |

The new check agrees with the full `--cst` root state on all 811 inputs
compared (227 corpus fixtures, 3 samples, 17 W06 inputs, 35 W07/W13 seeds,
485 truncated fixtures, 44 Session 05 probes; 391 of them with an error,
including the four recovery fixtures whose `MISSING` node the default output
hides). W06 now includes the 100,000-operand chain (0.26 s on Windows, 0.12 s
on the Ubuntu CI runner).

## Release gate and interpretation

- Gate (validation.md V10, workload W06): every input within 10 s and 1 GiB
  — met; the largest valid input measured (5 MB) needs 1.2 s and 156 MiB.
- No crash, hang, quadratic growth or unbounded memory was observed on valid
  or malformed input, and Session 05 changed no grammar file, so there is no
  regression from `SESSION_05_BASELINE` (`2aeb29d`). No optimisation was made:
  profiling found no material bottleneck.
- The slowest measured case is malformed input of an unresolved form (bare
  CR line endings, 0.2 MiB/s, linear).
- Limitations: one machine and one OS; Linux performance is only indirectly
  observed (CI W06 timings); the harness is not shipped; the comparison with
  the legacy grammar covers only syntax both accept.
