# 0.1.0 performance

Measured performance, memory, incremental and query baseline of grammar
version 0.1.0 (Session 05, 2026-09-23/24 UTC; recovery complexity was
investigated, one family fixed and the release parser re-measured in Session
05-1, 2026-09-24). It is a release baseline, not a speed claim: it states
what was measured on one machine. Two limitations are disclosed:
[KL-002](#known-limitation-kl-002), quadratic error-recovery time on long runs
of malformed prefix operators, and [KL-003](#known-limitation-kl-003),
quadratic error-recovery time and memory on long runs of malformed `^`
operators. A third family, unclosed calls and indexes, was
[fixed](#fixed-in-session-05-1-unclosed-calls-and-indexes-r-a-01). Every
number is an empirical observation for the inputs and machine below, not a
guarantee. Raw samples, inputs and scripts are local evidence:
`artifacts/session-05-final-release-freeze/04-performance/` (identity
`EVIDENCE-SHA256SUMS` = `0fa05e41965332762963d83d359ea1b36ee5e497b91bdd63b75a281a822b290d`)
and `artifacts/session-05-1-b01-recovery-complexity/` (root cause
`EVIDENCE-ROOT-CAUSE-SHA256SUMS` = `af400263fcbfde96fb0df4660dc29c97be8599bbc99b1b6918338a60a14e2449`;
re-audit `16-reaudit/EVIDENCE-REAUDIT-SHA256SUMS` = `d55d6b59afca6a5b8ea4cb2c836921d1ffb0cc414dd1cd639be6d8725cbe3b7f`;
release parser `EVIDENCE-POSTFIX-SHA256SUMS` = `8563f500405edcfe1cb7881b0accb996211ab91a7809ba2c289725e3adac4cc7`).

below 200 KB, 10 up to 2 MB and 5 above; one parser object, a fresh parse

accounting). Every input's error state was checked: all valid inputs parse
with no error, all malformed inputs with one.

## Known limitation KL-002

Found by the Session 05 final review (B-01), isolated in Session 05-1 and
widened by its re-audit (B2-02); record in
[validation.md](../validation/validation.md) (KL-002).

**Family.** A prefix operator (`+`, `-`, `not`) followed by a token that
cannot start an operand and forces the pending prefix operators to reduce
(`*`, `/`, `,`, `)`, `<`, …), repeated in one expression: `x = +*+*+*…`,
`x = (not)not)…`, also with spaces, inside closed `(…)` and `[…]`, after
`print`, `return`, `if`, `while`, `for`, `dim`, and in call arguments across
lines (`f(⏎-,⏎-,…`). Not affected (linear): `*/` repeated (no prefix
operator), `not *` repeated (`not` binds looser than `*` and is not reduced
before it), array elements across lines (`[⏎-,⏎…`), one malformed statement
per line.

**Scaling.** Witness `x = ` + `+*`×k + LF on the release parser, runtime
0.27.0. Native: p50 of 5 parses below 1 s, 3 below 5 s, 1 above; pinned CLI:
`--time`, median of 3.

| k | Bytes | Native | Pinned CLI |
|---:|---:|---:|---:|
| 250 | 505 | 21.6 ms | — |
| 500 | 1,005 | 85.8 ms | — |
| 1,000 | 2,005 | 333.5 ms | 434.5 ms |
| 2,000 | 4,005 | 1.50 s | 1.75 s |
| 4,000 | 8,005 | 5.67 s | 7.84 s |
| 8,000 | 16,005 | 29.5 s | not run |

The local exponent is 1.9–2.4 per doubling. The CLI exceeds W06's 10 s bound
from about 9 KB. Peak working set stays at or below 13.5 MiB (16 KB), and the
CLI process at or below 15 MiB (8 KB); no crash occurred. The `not` form
behaves the same (`x = (` + `not)`×2,000: 1.5 s native). Valid input of the
same size is linear (`x = 1` followed by `+1`×8,000: 5.5 ms; by `+-1`×8,000:
9.9 ms).

**Runtime and generator.** Measured on `fec46d21…` in Session 05-1: the
same curve (within host noise) appears with runtimes 0.25.1, 0.26.13 and
0.27.0, and with 0.27.0 after reverting any one of its recovery commits
`869638f6` (upstream issue #5910, a recovery tree-shape regression),
`f30ee2b3` or `15ea3328`; on three small witnesses these eight builds give
identical trees. Generators 0.26.13 and 0.27.0 produce byte-identical `src/`
files from this grammar. Neither a pin change nor a runtime choice removes
the limitation, and this repository does not ship a runtime.

**Cause.** Each malformed pair makes the runtime recover to the shallowest
earlier state that accepts the next prefix operator, which is the state after
the previous one, because prefix operators nest (`- -x`, BS-EXP-028). The
pending prefix operators therefore grow by one per pair, and the version that
inserted a missing operand reduces the whole pending chain again at the next
forcing token: the parse performs k² reductions (measured 1.000·k², constant
time per reduction), while every other recovery event is linear. A 13-rule
grammar with only assignments, prefix `+`/`-` and binary `+ - * /` shows the
same curve on runtimes 0.25.1, 0.26.13 and 0.27.0; removing prefix operators,
or forbidding a prefix operator directly inside another, makes it linear.
tree-sitter-python is also quadratic on members of this family
(`x = +/+/…`, `x = [-,⏎-,⏎…`). The grammar's part is the documented operator
structure (BS-EXP-012: prefix `+`/`-` binds tighter than multiplication) and
the nested encoding of prefix operators. No grammar change was found that
keeps both the accepted language and the nested `unary_expression` tree:
forbidding nesting rejects `- -x`, which 0.1.0 and BrighterScript accept;
lowering the prefix precedence contradicts BS-EXP-012 and still leaves `-)`
quadratic; a flat prefix-run encoding keeps the language and is linear in the
minimal grammar, but changes the public shape of `unary_expression`, which
the owner declined for 0.1.0.

**Realistic editing.** On the release parser, scattered errors stay at
valid-input cost: one 169 KB expression with 1, 10 or 100 `+ *` sites parses
in 19–24 ms (valid: 20 ms); a 120 KB program with 100 sites in 27 ms (valid:
23 ms); a 99 KB multi-line array with 100 malformed elements in 25 ms (valid:
18 ms). Inserting `* ` into the long expression and removing it again reparse
incrementally in 5.5 and 5.4 ms (fresh: 20 ms), in the program in 1.1 and
1.3 ms; each incremental tree equals the fresh one. The limitation needs
hundreds of consecutive malformed pairs.

**Mitigation.** A consumer that parses untrusted or generated text can bound
the parse time with the runtime's progress callback
(`ts_parser_parse_with_options`, `TSParseOptions.progress_callback`,
available in 0.25–0.27): on the 16 KB witness a callback that returns true
after 200 ms stopped the parse at 200.0 ms. Editors that reparse
incrementally are affected only while such a run exists in one expression.

**Release impact.** 0.1.0 ships with KL-002 disclosed. Its W13 witness
(k = 1,000) and its row of the recovery scaling guards
([validation.md](../validation/validation.md)) run locally and in hosted CI;
the guard fails if the curve becomes worse than quadratic, the k = 1,000
parse exceeds 3 s or its process exceeds 256 MiB.

## Fixed in Session 05-1: unclosed calls and indexes (R-A-01)

Found by the Session 05-1 re-audit (Reviewer A R-A-01, Reviewer B B2-01). A
run of unclosed calls or indexes, each opened with a token that cannot start
its content, in one expression or statement (`x = f(*f(*…`, `a[*`, `f(=`,
`a.b(*`, `a?.b(*`, `a@b(*`, `f(⏎*`, statement `f(=`), took quadratic time and
memory before the fix. Native, runtime 0.27.0, k = 2,000:

| Input | Bytes | Before (`fec46d21…`) | After (`6da8a470…`) |
|---|---:|---:|---:|
| `x = ` + `f(*`×k | 6,005 | 2.69 s, 1,269 MiB | 6.9 ms, 7.5 MiB |
| `x = ` + `a[*`×k | 6,005 | 2.84 s, 1,269 MiB | 7.4 ms, 7.5 MiB |
| `f(=`×k (statement) | 6,001 | 3.69 s, 1,472 MiB | 9.2 ms, 5.3 MiB |
| `x = ` + `a.b(*`×k | 10,005 | 3.50 s | 10.3 ms, 8.4 MiB |

Before the fix the pinned CLI needed 1.27 GiB at 6 KB, a `FAIL` of W06's
memory bound, on runtimes 0.25.1, 0.26.13 and 0.27.0 alike; the legacy
grammar and tree-sitter-python were linear on the same input (36 and 14 ms).
Cause: at end of input the runtime accepts the error version by popping every
path of its stack (`ts_parser__accept` → `ts_stack_pop_all`), copying a
subtree array per path; with the postfix operand inlined, recovery left a
stack that is one level deeper per repetition and merged at every level, so
the copies grow quadratically and stay allocated until the parse ends. No
progress callback runs in that step. A 13-rule grammar with calls reproduces
it when the call operand is inlined and is linear when it is not. The grammar
change keeps `src/node-types.json` and every valid tree; only recovery trees
of this family change. Its row of the recovery scaling guards is a regression
test (exponent ≤ 1.5, ≤ 1 s and ≤ 256 MiB at k = 2,000; the unfixed parser
fails all three).

## Known limitation KL-003

Found by the Session 05-1 re-audit (Reviewer B B2-01, Reviewer A R-A-08);
accepted by the owner for 0.1.0 as an explicit exception to the
bounded-memory condition for known limitations; record in
[validation.md](../validation/validation.md) (KL-003).

**Family.** A run of `^`, each followed by a token that cannot start an
operand, in one expression: `x = ` + `2^*`×k, `2^)`, `2^,`.

**Scaling.** Release parser, runtime 0.27.0 (native: one parse per size;
pinned CLI: `--time` median of 3, process peak memory):

| Input | Bytes | Native | Native peak | Pinned CLI | CLI peak |
|---|---:|---:|---:|---:|---:|
| `2^*`×1,000 | 3,005 | 54 ms | 28 MiB | — | — |
| `2^*`×2,000 | 6,005 | 165 ms | 83 MiB | 172 ms | 86 MiB |
| `2^*`×4,000 | 12,005 | 588 ms | 301 MiB | 592 ms | 326 MiB |
| `2^*`×8,000 | 24,005 | 2.12 s | 1,137 MiB | 2.45 s | 1,131 MiB |
| `2^)`×2,000 | 6,005 | 1.74 s | 8 MiB | 2.00 s | 13 MiB |
| `2^)`×4,000 | 12,005 | 8.08 s | 11 MiB | 8.98 s | 17 MiB |
| `2^)`×8,000 | 24,005 | 38.8 s | 19 MiB | not run | — |

With `*` both time and memory grow quadratically, and the CLI process passes
1 GiB near 23 KB. With `)` or `,` the time is quadratic by the KL-002
mechanism and memory stays small; the 10 s bound is passed near 13 KB.

**Cause.** The right-associative `^` (BS-EXP-011) keeps every pending right
operand on the stack, and with `*` the end-of-input acceptance described
under R-A-01 copies a subtree array per path of that deep, merged stack. A
13-rule grammar with only a right-associative `^` behaves the same (6 KB:
212 ms, 79 MiB). Wrapping the right operand in a hidden rule has no effect;
wrapping the left operand makes it linear but parses `2^3^2` as `(2^3)^2`;
stratifying the operands by precedence keeps the trees but not the memory
curve. No grammar change that keeps BS-EXP-011 and the tree was found. The
legacy grammar has no `^`.

**Mitigation.** The progress callback does not bound the `*` form: its cost
lies in the end-of-input acceptance, where no callback runs (a 200 ms limit
stopped the 24 KB input after 2.0 s; the `)` form stopped at 200 ms). A
consumer that parses untrusted text should bound the input size or run the
parser in a process with a memory limit. The behaviour needs thousands of
consecutive malformed `^` pairs; no realistic edit produces it.

**Release impact.** 0.1.0 ships with KL-003 disclosed. Its W13 witness
(k = 2,000) and its row of the recovery scaling guards run locally and in
hosted CI (exponent ≤ 2.5, ≤ 3 s and ≤ 512 MiB at k = 2,000; observed 1.7,
0.2 s and 86–89 MiB).

## Release gate and interpretation

- Gate (validation.md V10, workloads W06 and W13): every W06 input and W13
  seed within 10 s and 1 GiB — met on the release parser, the KL-002, R-A-01
  and KL-003 witnesses included; the largest valid input measured (5 MB)
  needs 1.2 s and 156 MiB. Larger KL-002 and KL-003 inputs exceed the bound;
  validation.md "KL-002, KL-003 and the V10 bound" states how this is
  recorded.
- No crash or hang was observed. Growth is linear on valid input and on every
  malformed family measured except KL-002 and KL-003, which are quadratic;
  KL-003 is also quadratic in memory. A recovery sweep of 135 malformed
  families on the release parser (k = 500 and 2,000) found no family outside
  KL-002 and KL-003 above an exponent of 1.5 or 256 MiB. The unclosed call and index family was quadratic in
  time and memory before the Session 05-1 fix and is linear after it.
- No optimisation was made beyond that fix. No profile was retained for the
  Session 05 measurements; the Session 05-1 causes were isolated with
  parse-event counts, an instrumented runtime, a generator and runtime matrix
