# v0.1.4 native parity candidate — HOLD

This is an engineering record, **not a release receipt**. v0.1.3 remains the
published version. The candidate targets source builds on Windows x64,
Ubuntu 24.04 x64 and macOS 15 Apple Silicon ARM64. Intel macOS and Linux ARM64
are outside this candidate. The release decision requires every native gate,
the repeated W12 oracle, the three-OS parity aggregation, independent review,
and a source-only Release plus a nonbinary evidence ZIP for the exact final
commit. A failed or missing item holds the release.

The `bb35ac3` raw records show the same W12 content SHA-256
`08539e44dc7a9926112bd8b633161e8dca06239eb43fa5a22647602bb86fd552`
on all three OS for 231 inputs. The 2,811 registered native tree digests and
1,533 deterministic budget-zero native result signatures also match across
those three host records. This is V6 evidence of *registered-input functional
equality* for that candidate, supported by the pinned Tree-sitter source (L3).
It is not a complete release PASS: the Windows and macOS native performance
gates failed. The existing L1 language requirements, V2–V5 fixtures and V10
robustness checks remain separate claims; V6 equality does not establish Roku
device behaviour (V8) or correctness for every input.

The first adversarial review of `bb35ac3` found four release blockers:
incremental controls caused `build_native_evidence.py` to fail; POSIX cleanup
could leave a child that closed stdout; macOS memory sampling saw only the
driver PID; and an incomplete comparator input could print a parity PASS.
Commits `b373fc5` and `718c8f2` added fail-closed evidence validation,
process-group cleanup and group footprint sampling. The follow-up preflight
passed on Ubuntu and macOS, including a closed-pipe child and a macOS child
that crosses the memory cap. These controls do not prove that a process which
creates a new session cannot escape the POSIX group. The macOS footprint cap
is sampled rather than a kernel-enforced Job-object equivalent.
The follow-up review found that a macOS orphan which continued writing to the
pipe was no longer sampled after its parent exited; `508f370` does not close
that case. It also found insufficient W12 manifest and tool-identity checks in
the release ZIP, and that a product-only source change did not trigger the
native workflow. The follow-up found one more release-ZIP gap: timed raw run
records were excluded from the normalized signature but lacked their own file
hash. The branch changes bind the full raw run file to its host record and add
a deletion control. The orphan control now requires a successful post-parent
group sample and accepts prompt descendant cleanup as a safe outcome; the
separate child-memory control still requires a measured memory-limit kill.
The evidence and orphan-control corrections passed their local controls and
independent static re-review. Hosted gates remain required for release.

The second macOS preflight on `6315456` exposed a process-group identity race:
the supervisor had already reaped the group leader before a later `killpg`
check. Apple's [`killpg(2)` manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/killpg.2.html)
defines `EPERM` as a target-permission failure. Numeric group reuse is a
plausible cause, not confirmed by the available log, so the path is treated as
unsafe. A follow-up branch change observes child exit with Python 3.14
[`waitid(..., WNOWAIT)`](https://docs.python.org/3/library/os.html#os.waitid)
and retains the leader PID until group inspection and signalling are complete.
The `29a5223` Ubuntu and macOS preflights each passed twice. This closes the
observed `EPERM` failure path for those runs; the sampled cap and process-group
escape limitations remain. The independent reviewer found no remaining P0–P2
in the reviewed correction paths. Full qualification still fails.

### Release requirements still in force

The three hosts use the same registered source inputs and native API cases,
the 17 result names of the existing qualification lane, and the existing
numerical gate bounds. The hosted lane records two byte-identical W12 runs on
each OS and rejects any gate failure before normalizing evidence. A separate
job compares W12 content, native trees, API signatures, incremental results,
candidate/tool identities and the exact gate list; OS-specific clock and
memory values remain in host records. The aggregate job runs only after all
three OS jobs succeed and verifies raw files before making a ZIP. The ZIP
contains normalized results, gate records, input/tool identities and raw
run records; it contains no compiled parser library.

Windows reports private commit under a Job object. Ubuntu applies `RLIMIT_AS`
to each supervised process and reports peak RSS. macOS samples the process
group's physical footprint through Apple's `libproc` interface. These are
different measurements, so equal byte counts across hosts are not claimed.
The current v3 time and growth limits have **not** been replaced with
predeclared OS-specific values; that issue acceptance criterion is still open.
Repeated macOS failures near some limits and intermittent cancellation
coverage remain blockers. A release cannot be obtained by silently raising
limits, discarding failed trials or reporting functional equality as a full
performance PASS.

## Verdict

**HOLD (V6/V10, L3).** The supported three-OS source-build and registered
functional comparisons have partial evidence, but the exact candidate has no
three-OS 17/17 qualification PASS or evidence ZIP. Windows and macOS have
repeated native performance or cancellation FAILs. The required OS-specific
performance acceptance policy is still open. Do not merge the draft PR, tag
v0.1.4, publish a Release or claim full three-OS functional qualification.
v0.1.3 remains the published source-only release.
