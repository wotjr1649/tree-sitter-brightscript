Measurements: Windows 11 x64, gcc 16.2.0 `-O2`, default 2 MiB stack, runtime
0.27.0 (`6070dbfe`) linked statically into small C harnesses, each run in a
Job-object supervisor (512 MiB commit, 15 s watchdog, 8 MiB output). Timed
points use 1 warmup and 3–5 runs; expensive 1 MiB points run once. "Patched
runtime" below means an experimental copy of runtime 0.27.0 with changes to
`lib/src/stack.c` (and, for the release variants, `lib/src/parser.c`). No
consumer can use it today. Evidence levels: every measurement is V10 (local
pathological input, time and memory limits). The mechanisms come from the
runtime source, which is Level 3. Three separate-context reviewers of the same
model reviewed the first round of findings, so their independence is limited.
The results marked "Session 07" below are the lead's alone and have not been
reviewed. Local evidence is in
`artifacts/session-05-2-structural-recovery-safety/resume-07/` and
`resume-08/` (not tracked).

## Causes

| Finding | Mechanism established | Evidence |
|---|---|---|
| B5-01 | Error recovery keeps equal-cost alternatives as extra stack links. At end of input `ts_stack_pop_all` walks every path. `stack__iter` limits only concurrent iterators (64), so the number of copied paths grows with the input: `x = ` + `+f([)`×400 gives 12,696 paths of about 2,000 subtrees and 145.6 MiB live. No progress callback runs in this step (169 ms without a callback at that size). | V10; L3. Allocator and runtime counters, stack graphs, and the same grammar with only the path enumeration bounded |
| B5-02 | A malformed run inside PRINT has two equal-cost readings: close the item and start a new juxtaposed one, or skip the closer and nest. The runtime merges them and orders the in-error version last, so the nested path is always a non-first link. `stack_node_release` recurses on non-first links, one level per repetition, and the default 2 MiB stack overflows near 20,000 repetitions. The crash is not limited to PRINT: at 20,000 repetitions 43 of 195 malformed families overflow, 25 of them in assignment, `return`, `if`, `while`, array and associative-array contexts (e.g. `x = ` + `-f(-)`×20,000). Only families that are linear on the patched runtime were tried at that size, so 43 is a lower bound. | V10; L3. Recursion-depth counters, stack graphs, a minimization, and the same grammar with an iterative release |
| A5-01 | Field and query cursors walk every hidden ancestor up to the nearest visible one. The runtime rebalances only generator repeat symbols. The right-recursive `_print_items` list of `79d565b` therefore puts item *i* at hidden depth *i*, which makes field lookup, index access and query within one long PRINT quadratic. | V10; L3 |

The hidden-structure variants tried did not change the end-of-input path
counts, the copied bytes or the recursion depth (peak memory within 0.05 %).
They were left-recursive PRINT lists and hidden wrappers around unary
operands, call arguments, array elements and associative-array values. Other
representations were not tried. Among those tried, A5-01 and the Session 05-1
PRINT memory fix (B4-01) pull in opposite directions on the stock runtime.
`repeat()` restores balanced trees and linear queries, but its end-of-input
path count grows with the number of malformed items (`print ` + `f([)`×4,000:
+341 MiB). That is why `79d565b` adopted the right-recursive list.

## Candidates compared on the registered checks

| Configuration | B5-01 memory (registered points) | Cancellation | B5-02 at 20,000 | A5-01 (1,000–32,000 items) | B4-01 guard |
|---|---|---|---|---|---|
| Current grammar, stock runtime | 145.6 MiB at 2 KB, cap at 4 KB | late: the end-of-input step is not interruptible | stack overflow | quadratic | pass |
| PRINT `repeat()`, stock runtime | same as current | late | not reached (memory) | linear | fail |
| PRINT `repeat()`, patched runtime (iterative release, bounded end-of-input paths) | ≤ 3.6 MiB, linear | still has callback-free steps; see below | all 12 points and 195 sweep families complete | linear, 0.95–1.08 × the `repeat()` stock time | pass (native harness) |

With both runtime changes and the `repeat()` grammar:

- Valid input keeps the same ordered trees (nodes, spans, fields, error and
  missing flags) as the current release parser. This held on the 1,348 valid
  inputs among 2,811 and on 408 reviewer inputs. The grammar has no
  `conflicts`, so error-free input has a single accept path and the path bound
  cannot change a valid tree.
- Error-recovery trees are identical on the 1,463 malformed inputs of that
  set and on 13 original-size inputs. They can differ from the current parser
  elsewhere (6 of 150 reviewer inputs, including the root kind). Recovery
  trees are not contractual.
- The corpus passes 228/228 and the highlight tests pass 2/2 through the
  pinned CLI (stock runtime).
- Incremental and repair trees equal fresh parses on 28 edit scripts,
  including W10 I01–I12 and E1–E6.
- Valid-input parse time is 0.94–1.14 × the current parser.

It still does not pass every check:

- The end-of-input step still runs without a progress callback. It is linear
  instead of quadratic, but it takes 117–774 ms on 140–560 KB malformed inputs.
  A cancellation budget that falls inside this step returns 108–320 ms late.
  The budgets of the fixed Session 07 list happened to fall outside it and
  returned at most 90.1 ms late. A check of fixed budgets alone therefore misses
  the defect.
- Memory is linear, but it has a large constant on some malformed families.
  At 1 MiB, seven of the eleven malformed families measured reach the 512 MiB
  experiment cap.
- Heavy error recovery is 1.10–1.27 × slower. The iterative release causes the
  slowdown.

The `repeat()` grammar is byte-identical to the grammar before `79d565b`
(`src/parser.c` `3f3eafd1…`). The pinned generator reproduces it twice, and
`node-types.json` is unchanged. Adopting it would change the generated-file
identities, the numeric symbol ids and the hidden rules. Without the runtime
changes it would also revive B4-01 for every consumer.

## Stricter criteria (Session 07)

Before any new candidate was measured, the owner's Gate A decision fixed six
additional checks. They are stricter than the earlier ones, and no earlier
bound was relaxed. Censored points (memory cap, watchdog, crash) count as
failures.

| Check | Bound |
|---|---|
| Callback gap | No interval without a progress callback longer than 100 ms, including the first call and the return |
| Overshoot | Return ≤ 100 ms after the budget, for budgets 25 ms–4 s |
| Cleanup | Tree and parser deletion ≤ 100 ms |
| Absolute memory | Peak commit ≤ 128 MiB on the registered points |
| Large input | Peak commit ≤ 256 MiB and ≤ 10 s on 1 MiB input |
| Query | Growth exponent ≤ 1.5 from 2,000 to 20,000 repetitions |

Results (Session 07) show the worst uncensored value per check. RT3R and RT3M
are two diagnostic runtime variants, both built on top of the patched runtime.
RT3R defers the stack release and checks the callback while it runs. RT3M
materializes one accept path only.

| Check | Current parser, stock runtime | `repeat()`, patched runtime | + deferred release (RT3R) | + one accept path (RT3M) |
|---|---|---|---|---|
| Callback gap | fail: 544.1 ms | fail: 375.3 ms | fail: 323.7 ms | fail: 180.4 ms |
| Overshoot | fail: +159.9 ms | fail (censored); timed points ≤ +90.1 ms | fail (censored); ≤ +89.4 ms | fail (censored); ≤ +39.1 ms |
| Cleanup | fail: 109–127 ms on valid 1 MiB PRINT | fail (censored); ≤ 97.1 ms | fail (censored); ≤ 80.0 ms | fail (censored); ≤ 80.4 ms |
| Absolute memory | fail: cap | fail: 255.5 MiB | fail: 255.4 MiB | fail: 173.7 MiB |
| Large input | fail: 8 malformed families at cap; valid PRINT 348 MiB | fail: 7 families at cap, 1 at 477 MiB | same | same |
| Query | fail: exponent 1.94–2.08 | fail: 1.94–2.07 | not run (query code unchanged) | not run |

RT3R leaves all 2,811 trees unchanged. When a parse is cancelled inside the
deferred release and then resumed, it equals a fresh parse. RT3M changes 26
malformed recovery trees. Neither variant is proposed. The KL-002 witness in
the check set cannot finish within the watchdog on any configuration, so
every configuration fails the gap, cleanup and memory checks by construction
at that point. This result is kept as a failure. The owner decides any
revision of the check set.

## Session 07 findings

- **S07-M01, callback-free steps (open, material).** Two steps run without
  a progress callback. The first materializes the end-of-input paths. The
  second releases the stack graph in `ts_stack_clear` (35/67/116 ms at
  16k/32k/64k prefix repetitions). Deferring the release removes the second
  step without changing any tree. Materializing one path shortens the first
  step but changes recovery trees, and up to 180.4 ms remain whose cause has
  not been isolated.
- **S07-M02, large-input memory (open, material).** Retained stack nodes
  and interior subtrees dominate. Materializing the accept paths adds
  40–144 MiB on top. Bounding the paths does not reduce the remainder, and no
  variant changes it.
- **S07-M03, highlight query (open, material; the cause is established and
  the finding extends to valid input).** There are two mechanisms:
  - On a node with many children, such as malformed `x = ` + `[`×20,000, the
    cursor's scan for later named siblings is quadratic. This is independent
    of the pattern, and a query rewrite cannot avoid it.
  - On left-deep chains, one query state per ancestor waits for a later field
    child. Valid code is affected: `x = a` + `.b`×20,000 (40 KB) takes 2.8 s,
    and `x = a` + `.b(1)[2]`×20,000 (160 KB) exceeds 15 s. Chains of only
    index access or only calls stay linear.

  A private rewrite of the member and attribute patterns to sibling order
  made member chains linear (10.8 ms). Captures were identical on 1,354 valid
  inputs, but they differed inside `ERROR` on 72 inputs (the records list 72;
  73 was a miscount, corrected 2026-09-25). The method-call
  pattern keeps mixed chains quadratic (11.8 s), and the shipped query is
  unchanged. This contradicts
  [0.1.0-release.md](0.1.0-release.md#performance), which states that the
  highlight query is linear in its captures except within long PRINT
  statements. It also contradicts the statement in
  [0.1.0-performance.md](0.1.0-performance.md) that no pathological query
  behaviour was seen.
- **S08-M01, valid 1 MiB PRINT on the current parser (open, material under
  the stricter checks).** Peak commit is 348 MiB and deletion takes
  109–127 ms. This is within W06 (1 GiB, 10 s) but fails the large-input and
  cleanup checks. With the `repeat()` grammar and the patched runtime the
  figures are 218 MiB and 81–84 ms.

## Gate A decision (2026-09-25)

- **Direction and scope.** The target direction is runtime-first, but only
  investigation is approved. The `repeat()` grammar and the patched runtime
  are not adopted, and no generator or runtime pin changes.
- **Condition for adoption.** Adoption would need a candidate that passes
  every check together and a supported runtime supply path. Neither exists
  (`RUNTIME_DEPENDENCY_UNRESOLVED`).
- **Upstream.** Nothing was posted automatically. The owner reproduces,
  writes and posts any upstream report personally, under Tree-sitter's
  contribution policy. Reproduction material was prepared locally.
- **Findings and limitations.** S07-M02 and S07-M03 stay material and
  blocking. KL-002 does not cover memory growth, crashes or query costs. It
  was not extended, and no new limitation was created.

## Other observations

- On the current parser, consider an edit that inserts an error in the middle
  of a long valid PRINT. The incremental tree's recovery shape then differs
  from a fresh parse; repair restores the original. Recovery trees are not
  contractual, and the W10 edits end in error-free text.
- On runtime 0.27.0, a parse cancelled during error recovery and then resumed
  can produce a recovery tree that differs from a fresh parse at the
  cancellation point. The stock runtime, the patched runtime and RT3R all
  behave this way.
