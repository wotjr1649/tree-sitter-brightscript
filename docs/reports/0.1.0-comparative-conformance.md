# 0.1.0 comparative conformance

Grammar version 0.1.0 compared with the historical Tree-sitter BrightScript
grammar and with BrighterScript (Session 05, 2026-09-23/24 UTC; rerun on the
release parser in Session 05-1, 2026-09-24), to answer
one question: for the claims this project makes, is 0.1.0 more accurate and
better supported than the historical grammar? Official Roku evidence (Level
1) decides every correctness conclusion ([source-policy.md](../provenance/source-policy.md));
acceptance by another parser is never evidence that a form is valid, and
rejection by 0.1.0 is a regression only where official evidence says the
form should parse. Raw results are local evidence: the Session 05 run on
`fec46d21…` (`artifacts/session-05-final-release-freeze/05-comparative/`,
identity `EVIDENCE-SHA256SUMS` = `e8504749c101f3001e82e18528ba8ab36076f674eb6c4cee775f19017c869ff7`)
and two Session 05-1 reruns: on the first fixed parser `6da8a470…`
(`artifacts/session-05-1-b01-recovery-complexity/18-comparative/`, identity
`EVIDENCE-POSTFIX-SHA256SUMS` = `8563f500405edcfe1cb7881b0accb996211ab91a7809ba2c289725e3adac4cc7`)
and on the release parser, reported below
(`artifacts/session-05-1-b01-recovery-complexity/23-final-parser/comparative/`,
identity `EVIDENCE-FINAL-PARSER-SHA256SUMS` = `7a2d64e267f2fb182b1c69dff08a26c442d6ceb593ae25df334ce97ef52599d3`).
For each of the 315 inputs of the Session 05 run, the first rerun gives the
same error state and S-expression for all three grammars; it adds the
BS-EXP-028 fixture and three Session 05-1 witnesses. The second gives the same
results again for every input it shares with the first, and replaces the
exponent witness's KL-003 name with KL-002 and adds two KL-002 witnesses.

## Method

Inputs (324): the 228 corpus fixtures, the 3 composite samples, the 40
W07/W13 robustness seeds, the 44 Session 05 deferred-finding probes, and 9
inputs written for the known regressions. For every input and grammar: whether the
tree has an error (root has-error state, hidden `MISSING` included) and the
S-expression.

Per requirement (`BS-*`, all 177 rows of the registry), keyed by its status:

- `documented` and `invalid` rows have official evidence. A legacy grammar
  is `BOTH_CORRECT` when it accepts every positive fixture and rejects every
  negative or recovery fixture, `NEW_BROADER_CORRECT` when it rejects a
  documented form, `NEW_STRICTER_CORRECT` when it accepts an input official
  evidence rules out, and `NEW_CORRECT` when it accepts the fixture but
  builds a different structure: a different operator grouping (checked for
  the precedence fixtures of BS-EXP-002, 011–020, 027 after normalising the
  legacy wrapper nodes) or a different number of top-level statements.
  `BOTH_CORRECT` is therefore an acceptance-level result; except for those
  two checks the legacy tree shape (which uses other node names) is not
  compared.
- `provisional`, `tolerated` and `unresolved` rows have no official winner:
  `OFFICIAL_UNRESOLVED`, whatever either grammar does.
- `out-of-scope` rows are semantic, runtime or compile-time rules the
  grammar does not enforce (grammar-contract non-goals): `NOT_COMPARABLE`.
  At least six of the 13 contain compile-time rules stated at Level 1 (BS-LEX-019,
  BS-LEX-023, BS-COND-014, BS-ERR-007, BS-EXP-026, BS-COND-011).

The two legacy identities gave the same error state for every one of the
324 inputs and the same category for every requirement; below, "legacy"
means both.

Validation level: V7 (comparison with other parsers; validation.md) over the
V3 fixture set. V7 shows where the grammars differ; which one is right is
decided only by the Level 1 evidence behind each requirement.

Of the 97 documented requirements, the legacy grammar handles 43 at the
acceptance level and misses or misparses 54; 0.1.0 passes all 97. Of the 6
invalid requirements, the legacy grammar accepts the invalid input of 3.

Legacy false accepts among the negative and recovery fixtures (7 of 29):
both BS-COND-013 fixtures, both BS-EXP-008 fixtures, `BS-STMT-017: WHILE
terminated by NEXT`, and the two BS-STMT-036 recovery inputs (`END IF`
closing a FOR body, `END SUB` closing a FUNCTION; known regression KR-005).

No documented or invalid requirement is handled correctly by the legacy
grammar and incorrectly by 0.1.0. The mirror case exists at input level in
two out-of-scope rows. For BS-COND-014 (the Level 1 constant-name character
set) both legacy identities report an error on the four designator probes
(`#const x$ = true` and three variants) that 0.1.0 accepts; for BS-ERR-007
(PS: a label inside a TRY block is illegal) both reject the guard fixture
`BS-ERR-007: label inside a TRY body is not rejected`. Both legacy
rejections are incidental (it rejects every type designator, including the
documented `a$ = 1`, and every label, KR-006), and 0.1.0's acceptance is a
disclosed non-goal.

## Malformed-input performance

Not a correctness result, and not part of the requirement matrix. On the
KL-002 family (repeated malformed prefix operators,
[0.1.0-performance.md](0.1.0-performance.md#known-limitation-kl-002)) the
legacy grammar is linear and much faster on the same runtime: `x = ` +
`+*`×4,000 (8 KB) takes 6.0 ms with legacy `0c534d56` and 5.7 s with 0.1.0
(runtime 0.27.0). The legacy grammar has no prefix `+`/`-` operator, so it
never builds the chain that makes recovery quadratic; the same absence makes
it reject documented prefix-operator syntax such as `a = -x * y` (BS-EXP-012,
a `NEW_BROADER_CORRECT` row). It has no `^` and no nested single-line IF
either, so those KL-002 families do not arise in it (`2^*` and `if a⏎*2` are
skipped linearly). On unclosed calls and indexes
(`x = f(*`×2,000) both grammars are linear since the Session 05-1 fix
(legacy 36 ms, 0.1.0 6 ms; before the fix 0.1.0 needed 2.7 s and 1.24 GiB).
Both facts hold: 0.1.0 is more correct on official syntax, and the legacy
grammar recovers faster from the KL-002 families.

Each defect is present in the legacy grammar and absent from 0.1.0; KR-001
is the only one fixed between the two legacy identities.

## BrighterScript (Level 4, static reading)

BrighterScript was read, not executed, so this column is qualitative. It is
consulted only as the registry's source policy allows:

- The 10 `tolerated` rows cite BrighterScript accepting the variant in plain
  BrightScript mode without an error diagnostic (for example
  `printStatement()` for BS-STMT-039, 040); 0.1.0 accepts them, the legacy
  grammar fails 8 of them.
- Where BrighterScript accepts a form 0.1.0 has no rule for, the row stays
  `unresolved` and says so: `sub … as T` (BS-FUNC-004), `endfor`
  (BS-STMT-021), line continuation after operators and in argument lists,
  which it enables from Roku OS 15.3 without Level 1 support (BS-EXP-023,
  024).
- Where BrighterScript reports errors that 0.1.0 does not, the rule is a
  compile-time rule the grammar does not enforce: designators on function
  names (BS-LEX-019), reserved words as names (BS-LEX-023).
- BrighterScript also reports errors for comma-first separators and a break
  after an associative-array `:` (BS-ARRAY-009, BS-AA-006), which 0.1.0
  rejects too; both are `unresolved`.
- BrighterScript-only syntax (classes, namespaces, template strings, `??`,
  typecasts, …) is out of scope (AMB-34); Session 04 checked that 0.1.0
  rejects it.

## Unresolved cases

The 25 `unresolved` requirements have no fixtures, only W13 seeds; their
results are recorded, not judged. Of the 40 seeds (the five Session 05-1
witnesses included), 0.1.0 reports an error for 35 and the legacy grammar for
30. The legacy grammar accepts line breaks
after operators, inside argument and parameter lists, multi-line strings,
bare CR, comma-first separators and TRY without CATCH; 0.1.0 has no rule for
any of them. Such differences are not correctness results.

Session 05 probes of deferred findings (44 inputs) differ between the
grammars in 25 cases; each is dispositioned in the registry (for example
PRINT separators BS-STMT-040 and `#error` without text BS-COND-015 are
tolerated and parse in 0.1.0 only; `x = 1 #const a = true` is an error in
0.1.0 only; the four designator probes of BS-COND-014 are errors in the
legacy grammar only; comma-first separators are unresolved).

## Conclusion

On the evidence above, 0.1.0 is more accurate and better supported than the
historical grammar for every claim this project makes with official
evidence: it parses all 97 documented and rejects the inputs of all 6
invalid requirements, where the legacy grammar misses or misparses 54
documented requirements, accepts invalid input of 3, and reproduces all six
known regressions. The comparison does not establish that 0.1.0 matches
Roku's compiler (no Level 2 evidence), says nothing about provisional,
tolerated or unresolved behaviour beyond recording it, and compares legacy
trees structurally only for operator grouping and statement boundaries.
It is not a performance comparison: on the KL-002 malformed families the
legacy grammar recovers faster (above).
