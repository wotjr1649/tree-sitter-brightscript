# 0.1.0 release

The release record of grammar version 0.1.0 (Session 05 and its
remediation continuation Session 05-1, 2026-09-24). It builds on the release
candidate ([0.1.0-release-candidate.md](0.1.0-release-candidate.md)) and its
independent audit ([0.1.0-release-audit.md](0.1.0-release-audit.md)), and
closes the items that audit deferred. The independent final review and the
verdict are at the end.

## Session 05-1 changes

The Session 05 final review found B-01 (quadratic error recovery on
repeated malformed prefix `+`/`-` operators, `PERFORMANCE_MATERIAL`), and
Session 05 stopped at `7d1c8c0` (`HOLD_FOR_RELEASE_REMEDIATION`). Session
05-1 isolated the cause: the Tree-sitter runtime's error recovery (runtimes
0.25.1, 0.26.13 and 0.27.0 alike) together with the documented operator
structure and the nested encoding of prefix operators; generators 0.26.13 and
0.27.0 emit identical files, and no grammar change keeps both the language
and the nested `unary_expression` tree. The owner accepted B-01 as KL-002.
Its independent re-audit of `e1a5da2` found a second mechanism, the
runtime's end-of-input acceptance: unclosed calls and indexes took quadratic
time and memory (1.27 GiB at 6 KB) because the postfix operand was inlined,
and runs of malformed `^` do so through the documented right associativity.
The owner approved the grammar fix for the first (`src/node-types.json`
unchanged) and accepted the second as KL-003, an explicit exception to the
bounded-memory condition for known limitations
([0.1.0-performance.md](0.1.0-performance.md#known-limitation-kl-003)).

### Maintainability

- Found: the binary identity check lived only in `check_generated.py` while
  four other paths ran the CLI; the asset and version logic would otherwise
  be repeated per script; the CI corpus step built its own environment.
- Changed: `scripts/tscli.py` is the single CLI path (identity, private
  parser and configuration directories, subprocess, timeouts, `parse`,
  `cst`, `has_error`), `check_generated.py` keeps only pin, lockfile,
  scanner and drift duties, and a structural test fails if a script names a
  CLI launcher or starts a program other than git, or a CI step runs a
  command outside its allowlist (`npm ci`, check scripts, git, without shell
  metacharacters; Session 05-1). Terminated processes are only the scripts'
  own children.
- Not changed: no grammar refactor. The textual duplicates in `grammar.js`
  are required (`_try_body` keeps `catch` an identifier outside TRY bodies,
  grammar-design §4; statement chains exclude optional chaining, §6) or
  would change `parser.c` for no concrete problem. Remaining debt: Markdown
  table parsing is repeated in `check_registry.py` and `check_schema.py`;
  the list of generated files appears in `check_v0.py` and
  `check_generated.py`; the `package.json` scripts run the npm binary
  directly (documented as conveniences, not evidence).

## Performance

[0.1.0-performance.md](0.1.0-performance.md): valid input from 852 B to
5 MB parses at 3–5 MiB/s (5 MB in 1.23 s, peak working set 156 MiB); deep
nesting and every valid scaling family grow linearly; incremental reparses
of nine kinds of edit take 1.3–1.8 % of a fresh parse and equal it; the
highlight query is linear in its captures. Recovery is linear on every
malformed family measured except two: repeated malformed prefix operators in
one expression take quadratic time (KL-002; 8 KB: 5.7 s native, 7.8 s
through the CLI), and repeated malformed `^` take quadratic time and, with
`*`, memory (KL-003; 24 KB: 2.4 s and 1.13 GiB through the CLI). Unclosed
calls and indexes took quadratic time and memory until the Session 05-1
grammar fix (6 KB: 2.7 s and 1.27 GiB before, 7 ms and 8 MiB after). No
other optimisation was made.

## Comparative conformance

[0.1.0-comparative-conformance.md](0.1.0-comparative-conformance.md):
against the legacy grammar (`253fdfaa`, `0c534d56`) on one runtime,
0.1.0 parses all 97 documented requirements and rejects the input of all 6
invalid ones; the legacy grammar misses or misparses 54 documented
requirements, accepts the invalid input of 3, and reproduces known
regressions KR-001–KR-006. No documented or invalid requirement is handled
correctly by the legacy grammar and incorrectly by 0.1.0; in two
out-of-scope rows (BS-COND-014 and BS-ERR-007) the legacy grammar rejects
inputs that 0.1.0 accepts as a disclosed non-goal. The legacy grammar
recovers faster from the KL-002 and KL-003 families, which it cannot build
because it has no prefix `+`/`-` and no `^`.

## Known limitations

- KL-002 ([validation.md](../validation/validation.md), details in
  [0.1.0-performance.md](0.1.0-performance.md#known-limitation-kl-002)):
  error recovery takes time quadratic in the number of consecutive
  malformed prefix-operator pairs (`+`, `-` or `not` followed by a token
  that forces the pending operators to reduce) in one expression; through
  the CLI such a run exceeds 10 s from about 9 KB. Memory stays small.
  Tree-sitter runtimes 0.25.1–0.27.0 behave alike; valid input and
  scattered errors are not affected. Consumers that parse untrusted text can
  bound parse time with the runtime's progress callback.
- KL-003 ([validation.md](../validation/validation.md), details in
  [0.1.0-performance.md](0.1.0-performance.md#known-limitation-kl-003)),
  accepted as an explicit exception to the bounded-memory condition: error
  recovery on a run of `^` each followed by a token that cannot start an
  operand takes quadratic time and, with `*`, quadratic memory (the CLI
  process passes 1 GiB near 23 KB). The cost lies in the runtime's
  end-of-input acceptance, which the progress callback does not interrupt;
  consumers that parse untrusted text should bound the input size or the
  parser's memory.
- No Level 2 (Roku device or compiler) evidence exists; V8 was not run.
  "Verified on Roku" is not claimed.
- Provisional (26), a disclosed grammar choice that Level 2 evidence may
  change: BS-LEX-003, 006, 008, 014, 024, 025, 028, 033, 035; BS-LIT-006,
  010, 017; BS-EXP-021, 027, 028; BS-STMT-008, 009, 020, 022, 026, 032, 033;
  BS-FUNC-003; BS-ERR-005; BS-COND-008, 012.
- Tolerated (10), non-normative and resting on Level 4 evidence: BS-LEX-011;
  BS-STMT-004, 011, 035, 039, 040; BS-FUNC-011; BS-ARRAY-003; BS-AA-004;
  BS-COND-015.
- Unresolved (25), not claimed either way: BS-LEX-007, 016, 020, 034;
  BS-LIT-013, 018; BS-TYPE-002; BS-EXP-022–025; BS-STMT-006, 014, 021, 028,
  034; BS-FUNC-004, 007, 012; BS-ARRAY-006, 009; BS-AA-006; BS-ERR-006;
  BS-COND-009, 010.
- Not rejected although the compiler would reject them (grammar-contract
  non-goals): reserved words used as names where they are not grammar
  keywords, literal words included (`step = 1`, `catch true`,
  `#const x = invalid`; BS-LEX-023), designators on function and constant
  names (BS-LEX-019, BS-COND-014), semantic rules (out-of-scope rows).
- Disclosed behaviour on invalid input: a word that begins with a contextual
  keyword or directive word may be split instead of rejected (`a modx`,
  `#iffy`); a label after code on the same line (`x = 1 : here:`) is
  accepted (BS-LEX-028, not contractual); inside a literal-false region a
  line whose first word is exactly `#if`, `#else` or `#end` is a directive
  (grammar-design §11); recovery
  trees are not contractual, and a missing block terminator can leave later
  declarations inside one `ERROR`.
- No language bindings, no WASM artifact, no package; consumers use `src/`.
- `go-treesitter`: V9 did not pass (recovery-tree differences in the Go
  runtime, `go-treesitter` KR-0005, on inputs with syntax errors). This
  repository makes no `go-treesitter` compatibility claim; the integration
  and its correction are separate work in that repository, on the released
  identity.
- Performance is measured on one Windows machine; the slowest measured
  families are KL-002 and KL-003; apart from them, malformed input with bare
  CR line endings (0.2 MiB/s, linear).
